## 2026-06-25 - Layout Thrashing in Scroll Listeners
**Learning:** Accessing `offsetTop` or `scrollHeight` inside high-frequency scroll events without throttling causes "layout thrashing" because the browser must synchronously recalculate the layout before returning the value. In single-page apps with many sections, this significantly impacts scroll performance.
**Action:** Always cache layout-sensitive values (like section offsets) in a variable and only update them when the layout actually changes (resize, view switch, content expansion). Use `requestAnimationFrame` to batch any DOM writes (like updating progress bars or classes) to ensure they happen at the start of the next frame.

## 2026-06-26 - Layout Thrashing in Mousemove Tooltip Tracking
**Learning:** Querying `tip.offsetWidth`, `tip.offsetHeight`, or calling `closest('[data-tip]')` inside a high-frequency `mousemove` handler triggers synchronous layouts and layout thrashing, causing visible frame drops. Setting `position: absolute` alongside manual `scrollX`/`scrollY` additions also forces unnecessary DOM reads. Promoting the tooltip to its own GPU compositor layer with `position: fixed` and `will-change: transform` allows the GPU to handle positioning seamlessly.
**Action:** Cache the tooltip's dimensions synchronously when it is first revealed (using a brief `visibility: hidden` measurement phase) and only consume these cached dimensions during movement. Throttle coordinate updates to the browser's refresh rate via a `requestAnimationFrame` gate, and avoid redundant DOM selector queries while the tooltip is already visible. Always copy high-frequency event properties to local variables to prevent event object recycling issues within async callbacks.
