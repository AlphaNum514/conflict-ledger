## 2026-06-25 - Layout Thrashing in Scroll Listeners
**Learning:** Accessing `offsetTop` or `scrollHeight` inside high-frequency scroll events without throttling causes "layout thrashing" because the browser must synchronously recalculate the layout before returning the value. In single-page apps with many sections, this significantly impacts scroll performance.
**Action:** Always cache layout-sensitive values (like section offsets) in a variable and only update them when the layout actually changes (resize, view switch, content expansion). Use `requestAnimationFrame` to batch any DOM writes (like updating progress bars or classes) to ensure they happen at the start of the next frame.

## 2026-08-12 - Layout Thrashing & GPU Composition in Tooltip Tracking
**Learning:** Querying layout-related metrics like `offsetWidth` or `offsetHeight` on high-frequency interaction events (like `mousemove`) forces synchronous, main-thread rendering/reflow calculations, causing frame drops. By caching tooltip dimensions when content resolves and promoting the tooltip to its own GPU compositor layer via `position: fixed` and `will-change: transform`, we completely bypass paint and layout pipelines. Throttling position updates with a requestAnimationFrame gate and copying coordinate values immediately upon event dispatch avoids event recycling issues and achieves silky-smooth cursor tracking.
**Action:** For all floating components (tooltips, popovers, dropdowns), use fixed-positioning with GPU-composited `translate3d(x, y, 0)` transforms. Implement synchronous dimension caching inside the activation handler, apply the initial coordinates synchronously before making the element visible to eliminate the first-frame pop-in flicker, and use requestAnimationFrame gating for mouse tracking.
